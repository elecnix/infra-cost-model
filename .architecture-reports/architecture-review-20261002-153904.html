C1 · One billing-scope resolver, not five pool algorithms

Strong

engine/engine.py L529–923 · pricing/{free_tiers,global_services,price_pools}.py

Problem

Five parallel functions each answer the same question — which pools share one bill? — each with its own guard condition and its own lookup table in the engine: _price_account_wide_pools, _price_shared_allowance_pools, _price_global_pools, _price_region_group_pools, _price_free_region_pools. Each was added by a separate bug fix (#294, #336, #338, #378, #389, #402). They call five different pricing predicates (free_tier_scope, shared_free_allowance, is_global_metric, price_pool, FREE_ALLOWANCE_REGIONS) to make overlapping decisions, and the precedence between them is encoded in the order of five pool_costs.update(...) calls.

The tables themselves are pure data and unified — all keyed (vendor, service, metric). The application logic is not unified, and that is where 36.9% of engine churn lands.

Solution

Move the question into the pricing layer as one resolver: billing_scope(provider, service, metric, region) → group of regions sharing one bill. The five algorithms collapse into one walk that asks the resolver once per pool instead of asking five predicates and reconciling the answers. Precedence becomes data in the pricing tables rather than control flow in the engine.

Benefits

  • Locality: “does this region share a bill?” lives in one function with one table, instead of five that must agree.
  • Leverage: the next overlapping-billing bugfix becomes a row in a table, not a sixth algorithm.
  • Tests: the five algorithms currently need full engine fixtures to reach; the resolver is testable as pure data→group.
  • The engine stops importing GCS-only FREE_ALLOWANCE_REGIONS for ~80 LOC of provider-specific branching.

Deletion test: deleting the five algorithms and re-expressing them as one resolver concentrates the precedence rule. This is the signal we want.

Before — shallow

_price_account_wide_pools → free_tier_scope()
_price_shared_allowance_pools → shared_free_allowance()
_price_global_pools → is_global_metric()
_price_region_group_pools → price_pool()
_price_free_region_pools → FREE_ALLOWANCE_REGIONS

5 overlapping guards. Precedence = call order. A table edit can silently reprice.

After — deep

engine: price one pool, split by quantity
billing_scope(vendor, service, metric, region)
← 5 tables, one precedence rule

One question, one owner. The engine never learns which regions share a bill.

C2 · The engine never validates the Cost model representation

Strong

engine/engine.py CostEngine.compute · schema/cost_model_schema.py · resources/types.py

Problem

validate_cost_model() exists and is correct, but its only callers are cmd_validate and the Python Surface. compute() checks the engine-version pin (Principle 14) and DAG acyclicity — and nothing else. Six paths produce $0.000000, exit 0, with no unpriced_metrics and no warning:

  • usage metric with unit but no value
  • fixed: true metric with no value
  • frequency: {value: 0}
  • edge rate: 0
  • pricingModel: percentage — reads the wrong key namespace (schema puts it on the metric, engine reads it off the node, default 0.0)
  • nodeType — schema-required, documented as decisive, read by nothing

Two nodes differ by 8 orders of magnitude on one field: shape: transactional, percentage_rate: 0.029, volume: 50 yields $7,670,250,000 without pricingModel and $0 with it.

Solution

Give the engine the same gate the CLI already has: call validate_cost_model() once in compute() and refuse rather than guess. Then consult the Resource representation for nodeType ↔ valid_metrics, which the registry already knows and the engine never asks.

Benefits

  • Leverage: one existing call converts an entire class of silent mispricing into a refusal. Principle 14 already set the precedent — the pattern exists, it is just not wired at the top.
  • Locality: every model invariant is enforced in one place, so “why did this price $0” stops needing three answers.
  • Tests: the six silent paths become six cheap negative tests at the seam, instead of end-to-end fixture tests asserting a zero total.

Deletion test: the complexity already exists in the schema and the handlers. Wiring the engine to it concentrates the check rather than moving it.

Touches Principle 14. That principle was written to make exactly this class of silent mispricing visible; today it only covers engine-version drift. Extending it is completing the principle, not contradicting it.

C3 · Stop catalog row names leaking into the Cost model representation

Strong

resources/*.py · examples/*.yaml · schema/cost-model.schema.json

Problem

valid_metrics is declared by all 36 handlers and read by nothing in the engine, the schema, the CLI or either Surface. Meanwhile AWS handlers lack a catalog_metrics mapping, so users are forced to write raw catalog row names into their Cost model representation:

# examples/data-pipeline.yaml:30
usageMetrics:
  S3-PutRequest: { unit: requests, value: 1 }
# but S3Bucket.valid_metrics advertises:
  putRequests · getRequests · storageGb

Three bundled examples do this. Azure and GCP were given proper logical names in f8c86ca; AWS was not. The pricing source's product-family naming has become the canonical Usage metric vocabulary, and it has reached the user's YAML.

Solution

Every handler declares a complete logical→catalog mapping; the registry resolves it. The schema validates metric names against valid_metrics. Catalog row names become private to the pricing layer.

Benefits

  • Locality: a pricing-source rename stops rippling into every Cost model representation in the wild.
  • Leverage: it makes the registry the single place that knows a Node type's metric vocabulary — the depth that already exists, finished.
  • Tests: descriptor-coverage tests can assert “every handler metric resolves to a row” instead of hand-listing Azure/GCP handlers (today AWS is uncovered — Bedrock and Secrets Manager metrics are unpriceable live).
This one is not a pure refactor. Existing models using S3-PutRequest would need migrating. The three bundled examples and the test suite are the migration surface; external models need a deprecation window.

C4 · One adapter from argv, not six written separately

Strong

cli.py (1092 LOC) — L61 vs L126/139/156 · L283…1001 · L614 vs L1041

Problem

The --catalog flag is inverted between command groups. Reproduced:

$ compute examples/serverless-api.yaml
Total Monthly Cost: $274.324502
$ whatif examples/serverless-api.yaml …
Baseline cost: $0.000000 # exit 0
$ whatif … --catalog
Baseline cost: $0.000104 # ≈ $274/mo

Same Cost model representation, same Cost engine, two answers differing by 100%. A budget gate built on whatif gets $0 and passes. Separately, the Path→exists→open→parse→except preamble is copy-pasted 8 times (~129 LOC) and the 4-way IaC format dispatch is duplicated verbatim twice.

Solution

One _load_model(path) → dict | _CLIError and one --catalog/--no-catalog pair with a single default, matching Principle 13 (“prices are queried”). One extract_for_format(data, fmt) in the registry, called twice instead of reimplemented twice.

Benefits

  • Locality: load errors and error wording are decided once; today each of the 8 sites can drift.
  • Leverage: removes an entire class of wrong answer for ~100 lines deleted.
  • Tests: ~24% of test_cli.py (412 of 1728 lines) is tempfile plumbing and near-duplicate YAML literals; a tmp_path fixture plus a _write_model() helper deletes essentially all of it.

Deletion test: pure repetition — deleting it concentrates the error-handling policy in one function. Highest leverage per line in the repo.

One surface. “Learn one, know all three” starts to hold.

C5 · Give the descriptor DSL a schema

Strong

pricing/sources/infracost.py — METRIC_DESCRIPTORS L727–1249 · sync_to_cache L411–521

Problem

243 descriptors (182 azure / 38 aws / 23 gcp) across 19 distinct field names, all interpreted by string literal inside one 110-line function. No schema, no validation, no type — an untyped mini-language whose interpreter is the most branch-heavy function in the pricing layer. A misspelled field is silently ignored.

The same module also owns the GraphQL client, session discovery, region mapping tables, free-tier injection and the Azure Retail fallback. Seven responsibilities, one file.

Solution

Split sync_to_cache into parse → select → store, and validate every descriptor against a declared field set at import time. Split the transport from the descriptor knowledge so tests can supply Price rows directly.

Benefits

  • Leverage: a descriptor typo today surfaces as $0 — the exact failure mode Principle 14 exists to prevent. Validation turns it into a startup error.
  • Locality: 243 entries of pricing knowledge stop sharing a module with an HTTP client and an auth path.
  • Tests: 7 test files hand-roll a ~20-line GraphQL catalogue matcher; injecting a transport lets them supply rows directly and deletes ~250 lines of duplicated wire-format plumbing.

Deletion test: extracting the descriptor knowledge into its own module moves code but concentrates the validation rule that currently has no owner. Worth it for the validation, not the file split.

C6 · Two adapters, no interface — decide whether there is a seam

Worth exploring

pricing/sources/{__init__,infracost,aws_pricing,azure_retail}.py

Problem

sources/__init__.py exports two sources side by side, implying a peer relationship that does not exist. There is no Protocol, no ABC, no shared signature — they disagree on arguments and return type, and agree only in that both write into a cache.

aws_pricing is not a peer but a callee of the Infracost adapter (called from seed_pricing_catalog and _sync_fallback), and azure_retail is nested inside it. This is the textbook “one adapter = hypothetical seam” case: two adapters, zero of the interface.

Solution

Decide, then commit in code. Either a real PriceSource protocol both satisfy — or drop the parallel exports and name the dependency honestly. aws_pricing.SERVICE_CODES covers only 4 services, so it is not a genuine second source.

Benefits

  • Locality: a reader stops inferring a pluggable architecture that is not there.
  • Leverage: if a second real provider ever arrives, the interface already exists — or is honestly absent.
Touches Principle 13: “A provider plugin architecture is premature. Use a normalized multi-cloud source until it doesn't cover a needed provider.” Half of that is implemented — the names are abstracted, the interface is not. Worth reopening only because the naming currently misleads.

C7 · 876 LOC of dead parallel pricing implementations

Worth exploring

resources/*.py — 38 _*_cost functions across 13 test files

Problem

38 _*_cost helpers totalling 876 lines have zero production callers — every reference is in a test file. The engine prices exclusively through PricingCatalog. Two implementations of the same domain logic exist; one is live.

The risk is divergence, not size: s3.py:146 prices storage at $0.023/GB while s3.py:36 documents the same number in prose — two copies of one fact.

Solution

Delete them and retarget the 13 test files at the live path. Or, if they are deliberate executable documentation of the pricing model, say so in the module docstring — otherwise they are a trap.

Benefits

  • Leverage: removes a silent-drift surface between prose, seed rows and live pricing.
  • Locality: one price per fact, in the pricing layer.

Deletion test: deleting them concentrates nothing — a judgement call, not a mechanical win. Needs a deliberate decision on intent.

C8 · Code generation is a printer nobody consumes

Worth exploring

codegen/generator.py (362) + schema_reader.py (176) · cli.py L960–975

Problem

generate_handler returns a string that the CLI prints to stdout. No file is written, nothing is checked in, no CI job invokes it. All 25 handler modules are hand-written. Its 19 tests assert the string compiles — correct scope for a printer, but it is tested as a printer and used as nothing.

It is also wrong where it runs: _derive_metrics turns Terraform attributes into usage metrics — a category error (memorySize, runtime are config, not consumption), and it emits no catalog_metrics, so a generated handler would find no rows and silently fall back to embedded rates.

Solution

Wire it up properly, or delete it. Leaving it is the one option that buys nothing.

For contrast, the one generated artifact that does work is sdk/ts/src/types.generated.ts — regenerated and drift-checked in CI (npm run build:types && git diff --exit-code). That is a real seam. It is generated from the Cost model representation schema, not from .tf files.

Benefits

  • Leverage: a dead module that looks load-bearing misleads every reader of the resources layer.
Touches Principle 10. Type generation from infrastructure-as-code is unimplemented; the ResourceAddress union type it promises does not exist on either Surface.

C9 · Scaffolding that exists only for tests

Worth exploring

loop.py · resources/external.py · resources/registry.py L72–97

Problem

  • loop.py (127 LOC) — a personal agent-loop harness at the repo root. Not packaged, not in CI, not documented, untested, and 22 ruff errors while the repo has no lint config.
  • ExternalServiceRegistry — wholly test-only; its stated purpose is already served by ExternalNode in the main registry.
  • _infer_provider + _provider_index — a hardcoded 20-entry dict serving a from_address(provider=…) parameter with zero callers; the four accessors around it are test-only.

Solution

Delete or relocate loop.py; delete the test-only registry and provider index.

Benefits

  • Locality: the repo root stops making readers distrust everything else in it.
  • Removes ~200 LOC with no behaviour change.

Deletion test: concentrates nothing, loses nothing documented or depended upon. Pure subtraction — do it first, it makes the rest of the stack cheaper to review.
